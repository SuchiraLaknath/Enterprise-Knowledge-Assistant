# Card Switch Architecture

## Context

This document describes the architecture of the card switch at Commercial Bank. It explains the main design choices, so that engineers can change the system safely and reviewers can judge the risks.

## Components

The card switch routes ISO 8583 messages between channels and card schemes. Each component has a named owner and a published service objective. Interfaces are versioned, so that one team can change its component without coordinating a release across the bank.

## Data flow and resilience

Two active nodes share traffic, with a secondary gateway route for failover. Requests carry a correlation id, so that a journey can be traced across systems. Timeouts and retries are bounded, because uncontrolled retries can turn a small failure into a larger one.

## Security considerations

Each acquirer link uses mutual TLS with certificates from the inventory. All traffic between components is encrypted in transit. Access to production follows the bank's access control standard.

## Known limitations

The design favours availability and a simple recovery path over peak efficiency. Capacity assumptions are reviewed each quarter, because customer behaviour changes around salary days and public holidays. Changes to the card switch go through architecture review before implementation.

## Design goals

The design of the card switch follows four goals: protect customer data, stay available during a partial failure, be simple enough to operate at night, and allow components to change independently. Where these goals conflict, customer protection comes first and availability second. A design decision that departs from these goals is recorded with the reason, so that a later review can check whether the reason still applies. Reference patterns from the architecture board are used wherever they fit.

## Deployment and operations

Changes reach production through the standard pipeline, which runs automated tests and a security scan before each release. Releases are rolled out gradually, and they stop automatically if error rates rise above the service objective. Dashboards show request rate, error rate and latency for each component, and alerts page the on-call engineer when an objective is at risk. Operational procedures for the card switch are kept in the runbook library, and each alert links to the relevant runbook.

## Capacity and future direction

Capacity is planned from the bank's transaction forecast, with headroom for salary days, festival periods and marketing campaigns. Load tests run before each peak period, and the results are compared with the previous test so that any regression is visible. Over the next year, the team plans to simplify the card switch by removing components that no longer earn their complexity. Any significant change will be reviewed against the design goals in this document before work starts.
